# เติมดี — ระบบสนับสนุนการตัดสินใจเติมสินค้าร้านขายของชำ

Prototype สำหรับพรีโปรเจกต์รอบที่ 3 ระดับ ป.ตรี. รันในเครื่อง บันทึกข้อมูลจริงด้วย SQLite และใช้ข้อมูลจำลองเริ่มต้น 500 SKU ไม่มี AI/ML และไม่มีระบบเงินเชื่อ

## เริ่มใช้งาน (ไม่ต้องติดตั้งไลบรารีเพิ่ม)

1. ติดตั้ง **Node.js 24.x** จาก https://nodejs.org/ ให้เครื่องรู้จักคำสั่ง `node`
2. เปิด Terminal ในโฟลเดอร์ `grocery-prototype` (บน Windows สามารถดับเบิลคลิก `start.cmd` เพื่อเปิดเซิร์ฟเวอร์แทนขั้นตอน 2–3 ได้)
3. รัน:

```powershell
node server.js
```

4. เปิด http://localhost:3000 ในเบราว์เซอร์ ใช้ Chrome/Edge รุ่นปัจจุบัน
5. หยุดเซิร์ฟเวอร์ด้วย Ctrl+C ที่ Terminal

ครั้งแรกระบบสร้าง `data/grocery.sqlite` และข้อมูลเดโมอัตโนมัติ เปิดครั้งต่อไปใช้ข้อมูลเดิม ไม่เขียนทับข้อมูลเดิม และใช้งานหลังติดตั้ง Node.js ได้โดยไม่ต้องเชื่อมต่ออินเทอร์เน็ต ไม่มี CDN หรือบริการภายนอก

ทดสอบ:

```powershell
node --test
```

สร้างข้อมูลเดโมล่วงหน้าได้ด้วย `node seed.js` (ไม่เขียนทับฐานข้อมูลที่มีสินค้าแล้ว) หาก npm ใช้งานได้ สามารถใช้ `npm start`, `npm test`, `npm run seed` แทนได้ ไม่ต้องรัน `npm install` ในเครื่องที่สร้างต้นแบบนี้ npm มีปัญหาการตั้งค่าพาธ จึงตรวจและรันด้วย `node` โดยตรงแล้ว

เปลี่ยนพอร์ต หรือใช้ฐานข้อมูลเดโมชุดใหม่โดยรักษาของเดิม:

```powershell
$env:PORT = '3001'
$env:DB_PATH = './data/demo-round3.sqlite'
node server.js
```

จากนั้นเปิด http://localhost:3001 เมื่อจะใช้ค่าเดิมให้เปิด Terminal ใหม่ หรือใช้ `Remove-Item Env:PORT` และ `Remove-Item Env:DB_PATH` การซ้อมคนละรอบควรตั้งชื่อไฟล์ฐานข้อมูลใหม่ ไม่จำเป็นต้องลบข้อมูลเดิม

## ฟังก์ชันที่ทำงานแล้ว

- **ภาพรวมร้าน**: ยอดขาย/จำนวนใบเสร็จวันนี้ จำนวน SKU สินค้าหมด ควรสั่งซื้อ มูลค่าคงคลังตามต้นทุน และตัวอย่างสินค้าเหลือเท่ากันแต่ขายต่างกัน
- **สินค้าและสต็อก**: ค้นชื่อ/SKU/barcode กรองหมวด แบ่งหน้า เพิ่ม/แก้ไขสินค้า บาร์โค้ดเว้นว่างได้และต้องไม่ซ้ำหากระบุ SKU ต้องไม่ซ้ำ ปรับวันรอ/วันสำรอง/รอบซื้อรายสินค้าได้
- **POS**: ค้นและเลือก หรือเครื่องสแกน USB แบบ keyboard ที่ส่งรหัส + Enter เพิ่มจำนวน/ลบสินค้า รับเงินสด แสดงเงินทอน ใบเสร็จและพิมพ์ผ่านเบราว์เซอร์
- **ตัดสต็อกอัตโนมัติ**: ราคาใช้ค่าจากฐานข้อมูล ไม่เชื่อราคาจากหน้าจอ บันทึกใบขาย รายการสินค้า และการเคลื่อนไหวพร้อมกัน หากสินค้าใดไม่พอ ยกเลิกทั้งรายการ ไม่บันทึกครึ่งหนึ่ง ป้องกันคำขอขายเดิมตัดสต็อกซ้ำด้วย request key
- **รับสินค้าเข้า**: จำนวนเป็นยอดบวกเพิ่ม ต้องมีเหตุผล/เลขเอกสาร
- **ตรวจนับ/ปรับยอด**: จำนวนเป็นยอดใหม่ที่นับจริง บันทึกส่วนต่างและเหตุผล ตรวจนับเป็น 0 ได้
- **ประวัติ**: 100 ใบเสร็จล่าสุด เปิดดูรายละเอียดได้ ประวัติการเคลื่อนไหวสินค้าล่าสุด 100 รายการต่อ SKU
- **คำแนะนำ**: ยอดขายย้อนหลัง 7/14/28 วัน อะไร/เมื่อไร/เท่าไร พร้อมสูตรและเหตุผล ส่งออกรายการซื้อวันนี้ทุกหมวดเป็น CSV อ่านภาษาไทยใน Excel ได้

จำนวนสินค้าเป็นจำนวนเต็มตามหน่วยขาย ไม่มีการชั่งน้ำหนัก/ทศนิยม ไม่มี VAT ส่วนลด คืนสินค้า เงินเชื่อ ระบบสั่งซื้อจริง หรือการรับเข้าจากคำสั่งซื้อ เครื่องสแกนฮาร์ดแวร์จริงยังไม่ได้ทดสอบ; ได้ทดสอบโดยกรอกรหัสแล้วกด Enter ซึ่งเป็นรูปแบบอินพุตเดียวกัน ไม่รองรับกล้องสแกนในรอบนี้

## เดโม 5–7 นาที

ควรใช้ฐานข้อมูลชุดใหม่เพื่อให้ตัวเลขด้านล่างตรงกัน ตั้ง `DB_PATH` เป็นชื่อใหม่ก่อนเปิด ไม่เปิดสองเซิร์ฟเวอร์ใช้ฐานข้อมูลเดียวกัน

1. **เปิดภาพรวม**: 500 SKU มีบาร์โค้ด 400 และไม่มีบาร์โค้ด 100 ตัวอย่างสาม SKU แรกเหลือ 12 เหมือนกัน แต่บะหมี่ขาย 4/วัน น้ำดื่ม 8/วัน และน้ำปลาขาย 6 ชิ้นใน 28 วัน
2. **เปิดแนะนำเติมสินค้า**: ค้น `SKU0001` แสดงบะหมี่พอ 3 วัน รอสินค้า 2 วัน สำรอง 1 วัน จึงควรสั่งวันนี้ 28 ซอง กดดูสูตรและตัวเลข
3. **ขายจริง**: หน้า POS กรอก `8850000000001` แล้ว Enter เพิ่มบะหมี่ 1 ซอง กรอก `SKU0005` แล้ว Enter เพิ่มขนมไม่มีบาร์โค้ด 1 ถุง รับเงิน 100 บาท ยอด 28 บาท ทอน 72 บาท
4. **ตรวจการตัดสต็อก**: สินค้าและสต็อก ค้น `SKU0001` เหลือ 11 ซอง ดูการเคลื่อนไหวพบขาย -1 ประวัติการขายมีใบเสร็จใหม่
5. **คำแนะนำตามสต็อก**: หลังขายบะหมี่ แนะนำซื้อ 29 ซอง (40 − 11) ค่าเฉลี่ยยังเป็น 4 เพราะยอดขายวันนี้ยังไม่ใช่วันเต็ม
6. **รับเข้า**: รับบะหมี่เพิ่ม 30 ซอง ระบุเลขใบส่งของ ยอดกลายเป็น 41 จากหน้าแนะนำเอาเครื่องหมาย “เฉพาะควรสั่งวันนี้” ออกแล้วค้น `SKU0001` กลายเป็นเพียงพอ 10.25 วัน อีกประมาณ 7 วันจึงควรสั่ง
7. **ปรับยอด**: หากตรวจนับจริงพบ 40 ซอง เลือก “ตรวจนับ” กรอก 40 พร้อมเหตุผล ยอดใหม่เป็น 40 ไม่ใช่ 81 ดูการเคลื่อนไหวพบ -1
8. **ข้อจำกัด**: ค้น `SKU0500` สต็อก 0 แต่ไม่มียอดขาย แสดง “ตรวจสอบก่อน” และไม่เสนอจำนวนซื้ออัตโนมัติ
9. ดาวน์โหลด CSV รายการซื้อ แล้วปิด/เปิดเซิร์ฟเวอร์ใหม่เพื่อแสดงว่าข้อมูลยังอยู่

ข้อมูลที่มาพร้อมงานใน `sample-data/` เป็นตัวอย่างจากวันที่กำหนดตายตัว (7 ต.ค. 2026) ส่วนฐานข้อมูลเมื่อเปิดครั้งแรกจะสร้างย้อนหลังจากวันปัจจุบันในเขตเวลา Asia/Bangkok ชื่อรุ่นและราคาทั้งหมดเป็นข้อมูลจำลอง ไม่อ้างว่าเป็นบาร์โค้ดหรือราคาจริงของผู้ผลิต สร้าง CSV ตัวอย่างใหม่ได้ด้วย `node export-samples.js` ไม่กระทบฐานข้อมูลที่ใช้งานอยู่ CSV เป็นไฟล์อ้างอิง ยังไม่มีหน้าจอนำเข้า CSV

## สูตรที่ใช้และความหมาย

กำหนด `D` = จำนวนวันย้อนหลัง, `Q` = จำนวนขายในช่วงนั้น, `A = Q/D` = ยอดขายเฉลี่ยต่อวัน, `S` = สต็อกปัจจุบัน, `L` = วันรอสินค้า, `B` = วันสำรอง, `R` = รอบซื้อ

| ค่า | สูตร | ความหมาย |
|---|---|---|
| วันคงเหลือ | `S / A` เมื่อ `A > 0` | ประมาณจำนวนวันที่ขายได้ตามอัตราเดิม |
| จุดสั่งซื้อ | `ceil(A × (L+B))` | ระดับสต็อกที่เริ่มควรสั่ง |
| เป้าหมายคงคลัง | `ceil(A × (L+B+R))` | ปริมาณที่ต้องการครอบคลุมก่อนรอบซื้อถัดไป |
| ซื้อวันนี้ | ถ้า `S <= จุดสั่งซื้อ` และ `A>0`: `max(0, เป้าหมาย−S)` | จำนวนที่เสนอ ณ วันนี้ |
| อีกกี่วันควรสั่ง | `max(0, floor(S/A−L−B))` | ประมาณจังหวะสั่งแบบระมัดระวัง |

ตัวอย่างบะหมี่: `Q=112, D=28, A=4, S=12, L=2, B=1, R=7` จุดสั่งซื้อ `ceil(4×3)=12` เป้าหมาย `ceil(4×10)=40` ดังนั้นซื้อวันนี้ `40−12=28` ซอง

ใช้ยอดขายเฉลี่ยเต็มความละเอียดในการคำนวณ แล้วปัดขึ้นเป็นหน่วยเต็มเฉพาะจุดสั่งซื้อและเป้าหมาย ตัวเลขบนหน้าจอแสดงทศนิยมไม่เกิน 2 ตำแหน่ง
ถ้าการปัดจำนวนวันลงได้ 0 แต่สต็อกยังสูงกว่าจุดสั่งซื้อ หน้าจอแสดง “ติดตามวันนี้” และจำนวนซื้อวันนี้ยังเป็น 0 เพื่อแยกการติดตามใกล้ถึงจุดสั่งออกจากการแนะนำซื้อทันที

ช่วงย้อนหลังใช้ **วันปฏิทินที่จบแล้วในประเทศไทย** ไม่เอาวันนี้ซึ่งยังขายไม่ครบวันมาหาร รวมวันที่ขายเป็นศูนย์ไว้ในตัวหาร เพื่อไม่ทำให้ค่าเฉลี่ยสูงเกินจริง หลังขายวันนี้ สต็อกเปลี่ยนทันที คำแนะนำปริมาณจึงเปลี่ยนได้ แต่ค่าเฉลี่ยจะเปลี่ยนเมื่อวันนั้นจบแล้ว

“วันสำรอง” เป็นค่าที่ผู้ใช้กำหนด ไม่ใช่ safety stock ที่ประมาณจากความผันผวนทางสถิติ หากไม่มียอดขาย ระบบไม่หารด้วยศูนย์และไม่กำหนดจำนวนซื้อให้ เพราะไม่ทราบว่าเป็นสินค้าใหม่ ขายช้า หรือขาดนานจนขายไม่ได้ ยอดขายที่เกิดขึ้นจริงไม่เท่ากับความต้องการทั้งหมดเมื่อของขาด

ไม่มีสินค้าระหว่างสั่งซื้อ จึงใช้สต็อกที่มีแทน inventory position คำแนะนำไม่ใช่ใบสั่งซื้อ และยังไม่หักยอดสั่งที่ร้านอาจมีอยู่ ผู้ใช้ต้องตรวจสอบก่อนซื้อซ้ำ ไม่มี MOQ จำนวนยกลัง อายุสินค้า เทศกาล โปรโมชัน งบซื้อ หรือความจุชั้นวาง วิธีนี้เป็น baseline สำหรับทดลอง ไม่ใช่การพิสูจน์ว่าลดสินค้าขาดได้แล้ว

## โครงสร้างสำหรับพัฒนาต่อ

```text
grocery-prototype/
  server.js              HTTP server, API routes, static files
  db.js                  schema, transactions, deterministic demo generator
  service.js             POS, stock, product validation, recommendations
  seed.js                create demo without overwriting existing data
  public/
    index.html           page shell/navigation
    app.js               vanilla JavaScript screens and API calls
    style.css            responsive styles and receipt printing
  test/core.test.js       core and HTTP integration tests
  sample-data/            CSV samples for inspection, not auto-imported
  docs/PROJECT-NOTES.md   design, evaluation plan, advisor Q&A
  data/grocery.sqlite    runtime database (created automatically)
```

เลือก JavaScript ภาษาเดียวทั้งหน้าเว็บและเซิร์ฟเวอร์ ไม่ต้องเรียน framework/build tool ก่อนเดโม SQLite เป็นไฟล์เดียว สำรองง่าย และ `node:sqlite` มีใน Node.js ที่ใช้ จึงไม่มี dependency ภายนอก ดูเอกสาร https://nodejs.org/api/sqlite.html (ใน Node.js 24 อาจแสดง ExperimentalWarning ได้)

### ตารางฐานข้อมูล

- `products`: SKU, barcode nullable, ราคา/ต้นทุนเป็นจำนวนเต็มสตางค์, stock, L/B/R
- `sales`: ใบขาย เวลา UTC, ยอดรวม/เงินรับ, request key ไม่ซ้ำ
- `sale_items`: FK ไปใบขายและสินค้า จำนวน และราคาขณะขาย เก็บราคาเดิมได้แม้ภายหลังเปลี่ยนราคาสินค้า
- `stock_movements`: ยอดตั้งต้น/ขาย/รับ/ปรับ จำนวนเปลี่ยน ยอดหลังเปลี่ยน เหตุผล FK ไปสินค้าและใบขาย
- `meta`: วันที่สร้างข้อมูลเดโม

`products 1 → N sale_items N ← 1 sales` และ `products 1 → N stock_movements` ใบขายมี stock movements เชื่อมด้วย sale_id เงินเก็บเป็นสตางค์ลดข้อผิดพลาดทศนิยม SQL ใช้ parameter binding และ constraint ป้องกัน stock ติดลบ

### API

| Method / path | หน้าที่ |
|---|---|
| GET `/api/products` | รายการสินค้าทั้งหมด |
| POST `/api/products` | เพิ่ม/แก้ไข metadata สินค้า; ไม่เปลี่ยน stock |
| GET `/api/dashboard` | สรุปภาพรวม |
| GET `/api/recommendations?days=28` | ช่วงย้อนหลัง/คำแนะนำ |
| POST `/api/checkout` | ขาย: `{request_key, items:[{product_id,quantity}], paid_cents}` |
| POST `/api/stock` | `{product_id,type:'receive' หรือ 'adjust',quantity,note}` |
| GET `/api/sales` | 100 ใบขายล่าสุด |
| GET `/api/sales/:id` | รายละเอียดใบขาย |
| GET `/api/movements/:id` | การเคลื่อนไหวของสินค้า |

### การทดสอบที่ตรวจแล้ว

`node --test` ผ่าน **7 ชุด**: ข้อมูล 500 SKU/ledger, checkout แบบ atomic/idempotent, รับและปรับยอด/ไม่มีประวัติ, เพิ่มสินค้า/รหัสซ้ำ, ขอบเขตวันประเทศไทย, persistence, HTTP integration ทดสอบในฐานข้อมูลชั่วคราว ไม่แก้ข้อมูลเดโมที่ใช้งาน

ทดสอบหน้าจอจริงด้วยกรอกรหัสและ Enter: เพิ่มบะหมี่และขนมไม่มี barcode ชำระ 100 ยอด 28 ทอน 72, สต็อกบะหมี่ 12→11, รับเข้า 30 เป็น 41, และคำแนะนำเปลี่ยนเป็นเพียงพอ ทดสอบเพิ่มเติมก่อนนำเสนอ: ทดลองเครื่องสแกนจริง, ทดลองพิมพ์ใบเสร็จ/CSV ในเครื่องที่จะเดโม และซ้อมตามขั้นตอนด้านบน

### ขอบเขตการใช้

เป็นต้นแบบในเครื่องสำหรับผู้ใช้คนเดียว เซิร์ฟเวอร์ฟังเฉพาะ `127.0.0.1` ยังไม่มี login/roles, ไม่มี deployment หรือระบบสำรองอัตโนมัติ อย่าใช้เป็นระบบขายจริงก่อนเพิ่มการควบคุมผู้ใช้ การสำรองและขั้นตอนกู้ข้อมูล การคืนสินค้าและการตรวจยอด

สำรองโดยหยุดเซิร์ฟเวอร์ก่อนแล้วคัดลอกโฟลเดอร์ `data` ทั้งโฟลเดอร์ เก็บไฟล์ต้นฉบับไว้เสมอ โดยเฉพาะถ้ามี SQLite WAL/SHM ประกอบ อย่าคัดลอกแค่ไฟล์หลักในขณะที่เซิร์ฟเวอร์กำลังเขียน

## แนวทางต่อยอดรอบถัดไป

1. เก็บข้อมูลจริงกับร้าน ตรวจ SKU/หน่วย วันเปิดร้าน lead time และเหตุการณ์สินค้าขาดให้ถูกต้อง
2. เปรียบเทียบกับ low-stock แบบเกณฑ์ตายตัว โดยใช้ข้อมูลชุดและช่วงเวลาเดียวกัน
3. เพิ่มการสั่งซื้อและสินค้าในระหว่างรอ เพื่อคำนวณ inventory position ลดการซื้อซ้ำ
4. ทดลองวิธีพื้นฐานสำหรับสินค้าขายไม่สม่ำเสมอ/ค่าเฉลี่ยเคลื่อนที่ เปรียบเทียบความคลาดเคลื่อนก่อนเลือกวิธี
5. เพิ่ม import CSV, แยก frontend modules, auth และ backup เมื่อจะใช้งานจริง

อ่านแนวตอบอาจารย์และแผนประเมินใน `docs/PROJECT-NOTES.md`

### การแสดงจำนวนวันบนหน้าจอ

หัวข้อ “ขายได้อีกประมาณ” หมายถึงสต็อกปัจจุบันจะขายได้นานเท่าไรตามอัตราขายเฉลี่ย แสดงวันเต็มโดยปัดลง เช่น 3.6 วัน → ประมาณ 3 วัน; ถ้าน้อยกว่า 1 วันแสดงข้อความนั้น และสต็อก 0 แสดง “สินค้าหมด” ส่วนสินค้าที่ไม่มีประวัติและยังมี stock แสดง “ยังประเมินไม่ได้” ยอดขายเฉลี่ยในหน้าตารางแสดงจำนวนเต็มโดยปัดใกล้ที่สุด เช่น 3.64 → ประมาณ 4 ถุง/วัน; ถ้าขายเฉลี่ยมากกว่า 0 แต่น้อยกว่า 1 แสดง “น้อยกว่า 1” เพื่อไม่ทำให้เข้าใจว่าไม่ขายเลย รายละเอียดสูตรยังแสดงค่าทศนิยม สูตรและคำแนะนำยังใช้ค่าเต็มความละเอียด
