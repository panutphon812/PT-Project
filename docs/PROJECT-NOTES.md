# บันทึกออกแบบและแนวตอบอาจารย์

## ประเด็นของงาน

หัวข้อชั่วคราว: ระบบสนับสนุนการตัดสินใจเติมสินค้าสำหรับร้านขายของชำโดยใช้ข้อมูลการขายและสินค้าคงคลัง

POS เป็นส่วนเก็บข้อมูลการขาย การรับเข้าและปรับยอดช่วยรักษาสถานะคงคลัง ส่วนที่ศึกษาเป็นการนำข้อมูลเหล่านั้นมาช่วยตัดสินใจว่า **สินค้าอะไรควรเติม เมื่อไร และเท่าไร** พร้อมเหตุผลที่ตรวจสอบได้ หลักการ Reorder Point และค่าเฉลี่ยมีอยู่แล้ว ไม่อ้างว่าเป็นนวัตกรรมใหม่ หรืออ้างว่าระบบสำเร็จรูปไม่มีฟังก์ชันแบบนี้

ต้นแบบนี้แสดงความเป็นไปได้ของ core flow; ยังไม่ได้ทดลองกับร้านจริงหรือพิสูจน์ประสิทธิผล

## การไหลของข้อมูล

1. ระบุสินค้า: SKU บังคับ, barcode เป็นทางเลือก
2. POS ค้น/สแกน → ตะกร้า → รับเงิน → เซิร์ฟเวอร์อ่านราคาและตรวจ stock
3. transaction เดียวเขียน sales + sale_items + stock_movements พร้อมลด products.stock
4. ถ้าทำไม่สำเร็จ rollback ทั้งหมด; request key เดิมคืนใบเสร็จเดิม
5. รับเข้าเพิ่มยอด หรือตรวจนับแทนยอด; ทุกครั้งบันทึกการเคลื่อนไหวและเหตุผล
6. รวมยอดขายราย SKU ย้อนหลังเฉพาะวันเต็ม คำนวณ A, วันคงเหลือ, จุดสั่งซื้อและเป้าหมาย
7. dashboard และหน้าแนะนำอ่านผลล่าสุด ไม่เก็บคำแนะนำค้างไว้ในฐานข้อมูล

ข้อกำหนดสำคัญ: ทุก SKU มีหน่วยขายเดียว ราคา/ต้นทุนเก็บเป็นสตางค์ ไม่อนุญาตจำนวนติดลบ หรือจำนวนทศนิยม สินค้าใหม่เริ่มจาก stock 0 เพื่อให้รับเข้าและตรวจสอบร่องรอยได้

## คำถามที่คาดว่าจะพบ

**ทำไมไม่ซื้อ POS?**

POS สำเร็จรูปมีความสามารถมากอยู่แล้ว จุดประสงค์ของงานคือศึกษาแนวทางใช้ข้อมูลของร้านเพื่อช่วยตัดสินใจเติมสินค้า POS ในต้นแบบเป็นเครื่องมือเก็บข้อมูลและแสดงการเชื่อมโยงครบกระบวนการ ไม่ได้อ้างว่าจะทดแทนระบบเชิงพาณิชย์ทั้งหมด

**มีคนทำแล้วไหม?**

มีครับ ค่าเฉลี่ยและ Reorder Point เป็นหลักการที่มีอยู่ งานระดับนี้มุ่งประยุกต์ในบริบทร้านตัวอย่างและประเมินกับวิธีเดิม ต้องตรวจงานที่เกี่ยวข้องต่อและปรับวัตถุประสงค์กับอาจารย์ ไม่กล่าวอ้างความใหม่ของสูตร

**รู้ได้อย่างไรว่าจะหมดเมื่อไร?**

เป็นค่าประมาณจาก stock หารยอดขายเฉลี่ย หากเหลือ 12 ซอง และขายเฉลี่ย 4 ซอง/วัน ประมาณว่าพอ 3 วัน ไม่ใช่คำรับประกันว่าจะหมดในวันนั้น เพราะความต้องการอาจเปลี่ยน

**ทำไมซื้อ 28 ซอง?**

เฉลี่ย 4/วัน รอสินค้า 2 วัน สำรอง 1 วัน รอบซื้อ 7 วัน จึงตั้งเป้าครอบคลุม 10 วัน หรือ 40 ซอง เหลือ 12 จึงเสนอ 28 ซอง ณ จุดสั่งซื้อ ไม่ใช่จำนวนที่ระบบเรียนรู้จาก AI

**ทำไมวันนี้ขายแล้วค่าเฉลี่ยไม่เปลี่ยน?**

วันนี้ยังไม่จบวัน ถ้าเอายอดขายบางชั่วโมงไปแทนวันเต็มจะทำให้ค่าเฉลี่ยลดลงผิดจังหวะ จึงใช้วันเต็มก่อนหน้า แต่ stock ปัจจุบันเปลี่ยนทันที ทำให้คำแนะนำจำนวนเปลี่ยนได้ทันที

**ทำไมใช้ 28 วัน?**

เป็นค่าเริ่มต้นที่อธิบายง่ายและครอบคลุม 4 สัปดาห์ ไม่อ้างว่าเหมาะที่สุด มี 7/14/28 วันให้เปรียบเทียบ ต้องทดลองกับข้อมูลจริงเพื่อเลือกช่วง ไม่เลือกเพราะผลเดโมดูดี

**ถ้าไม่เคยขายหรือของหมดนาน?**

แสดงตรวจสอบก่อน ไม่หารด้วยศูนย์และไม่ให้จำนวนอัตโนมัติ ยอดขายเป็นศูนย์ไม่ได้แปลว่าความต้องการเป็นศูนย์ การเก็บช่วงของขาดและวันเริ่มขายเป็นงานต่อไป

**500 SKU เป็นข้อมูลจริงหรือไม่?**

เป็นข้อมูลจำลองเพื่อทดสอบการค้นหา การแบ่งหน้า และการเชื่อมโยงธุรกรรม มี 6 หมวด สินค้าไม่มี barcode 100 รายการ ยอดขายบาง SKU เป็นศูนย์เพื่อแสดงข้อจำกัด ไม่ถือเป็นหลักฐานการลดสินค้าขาดของร้านจริง

**แนะนำแล้วซื้อซ้ำได้ไหม?**

รอบนี้ไม่มีระบบ purchase order จึงยังไม่รู้ของที่กำลังส่ง คำแนะนำเป็นรายการให้เจ้าของร้านตรวจสอบเท่านั้น หากจะใช้จริงต้องเพิ่มยอดสั่งค้างก่อน

## แผนประเมินสำหรับรายงาน (ยังไม่ได้ดำเนินการ)

แยกความถูกต้องของโปรแกรมออกจากประสิทธิผลในการช่วยร้าน

| ประเด็น | วิธีเก็บข้อมูล | ตัวชี้วัด |
|---|---|---|
| ความถูกต้องของสต็อก | ทำรายการขาย/รับ/ปรับแล้วเทียบกับ ledger และยอดตรวจนับ | จำนวนครั้งยอดคลาดเคลื่อน |
| ความถูกต้องของสูตร | คำนวณมือบน SKU ที่คัดไว้เทียบผลระบบ | จำนวนกรณีตรง/ไม่ตรง |
| เวลาจัดรายการซื้อ | จับเวลาวิธีเดิมและระบบกับ SKU/โจทย์เดียวกัน | นาทีต่อรายการซื้อ จำนวน SKU ที่ตกหล่น |
| ปัญหาสินค้าขาด | บันทึกวันของขาดและความต้องการที่ขายไม่ได้จริง | stockout days ต่อ SKU ต่อช่วงติดตาม |
| ภาระคงคลัง | ตรวจนับและประเมินต้นทุนเป็นระยะ | มูลค่าคงคลังเฉลี่ย และสินค้าเกินจำเป็น |
| ความเข้าใจผู้ใช้ | ให้เจ้าของร้านอธิบายเหตุผลจากหน้าจอและทำงานตัวอย่าง | งานสำเร็จ/ข้อผิดพลาด/ข้อเสนอแนะ |

ต้องควบคุมหรือบันทึกความแตกต่างของโปรโมชัน วันหยุด การเปิดร้าน การส่งสินค้า และการเปลี่ยนราคา ไม่สรุปเหตุและผลจาก before/after เพียงครั้งเดียว การจำลองย้อนหลังควรใช้ข้อมูลที่ทราบ ณ วันนั้นเท่านั้น ห้ามใช้ยอดขายอนาคตในค่าเฉลี่ย และควรเทียบเกณฑ์ low-stock ภายใต้ lead time/งบประมาณเดียวกัน

การลดของขาดและการลด stock ต้องวัดร่วมกัน เพราะเติมมากอย่างเดียวอาจลดของขาดแต่เพิ่มเงินจม ข้อมูลเดโม 28 วันไม่เพียงพอสำหรับอ้างผลทางวิชาการ ควรตกลงระยะเก็บข้อมูลจริงและขอบเขตประเมินกับอาจารย์ก่อน

## จุดที่ควรพัฒนาต่อในโค้ด

- แยก `public/app.js` เป็น module ตามหน้าจอเมื่อระบบโตขึ้น
- เติม product activation/ประวัติเริ่มขาย เพื่อเลือกตัวหารสำหรับสินค้าใหม่อย่างเหมาะสม
- เพิ่ม test สำหรับ business rules ใหม่ก่อนเพิ่มคืนสินค้า ยกแพ็ก หรือคำสั่งซื้อ
- แยก API error สำหรับ validation กับ internal error เมื่อ deploy และเพิ่ม authentication
- เพิ่ม migration version และ backup/restore ก่อนเปลี่ยน schema ที่มีข้อมูลจริง

ไฟล์ synced ใน `sources/` ไม่ได้ถูกแก้ไข โค้ดต้นแบบอยู่ในโฟลเดอร์แยกต่างหาก
